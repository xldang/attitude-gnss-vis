# attitude-gnss-vis — 载体姿态敏感型卫星可见性及 PDOP 仿真

单文件 Web 科研工具。导入 RINEX 3.04 广播星历与带姿态的载体轨迹，实时计算
**天线面实际可见的卫星数量**、**PDOP** 与**定位/测速精度**，并以双视角星空图和联动曲线呈现。

**English version: [README.en.md](README.en.md)**

---

## 特点

- **单文件、零依赖、完全离线**。`gnss_pdop_tool.html` 一个文件装下全部 HTML/CSS/JS，
  双击即可用，浏览器直接 `file://` 打开即可运行，不发起任何网络请求。页面内含
  20 项自检，用户打开就能看到算法是否自洽。
- **七系统**：GPS、北斗 BDS、GLONASS、Galileo、QZSS、SBAS、NavIC。开普勒型
  （G/E/C/J/I）走广播星历传播，状态矢量型（R/S）直接做二阶位置外推。
- **姿态敏感**：掩角定义在天线面法线上，不是地理高度角。载体一动，掩角锥跟着动。
- **批量任务**：固定一份输入、多选另一类输入，起点按显式规则锚到同一绝对时刻，
  用来回答"换一天星历会差多少"或"换一条航迹会差多少"。单任务界面原样保留。
- **数值可验证**：仓库内含一份**用 Python 独立重写的参考实现**（`reference/ref_pdop.py`）
  和两套测试，JS 与 Python 互为交叉验证；另有一份真实接收机实测基准做回归。

## 快速开始

```bash
git clone https://github.com/xldang/attitude-gnss-vis.git
cd attitude-gnss-vis
# 直接双击 gnss_pdop_tool.html，或：
start gnss_pdop_tool.html          # Windows
```

页面上依次选择两个样本文件：

| 输入项 | 样本路径 |
|---|---|
| 星历 | `samples/rnx/BRDM00DLR_S_20262690000_01D_MN.rnx` |
| 轨迹 | `samples/traces/flight_shanghai_xian_5000.csv` |

跑完后拖动"高度角截止（掩角）"滑块（0°–45°，默认 15°），两张曲线与两张星空图
立即重算。点击"导出科研数据"可下载逐历元 CSV：表头固定为标准 7 列
（`Time`/`Longitude`/`Latitude`/`Height`/`Yaw`/`Pitch`/`Roll`）加
`Visible_Count` / `PDOP` / `PRN_label` 三列，再加上定位与测速精度五列
（`PosAccH_m` / `PosAccV_m` / `VelAccE_mps` / `VelAccN_mps` / `VelAccD_mps`），
与输入文件长什么样无关。

## 输入数据规范

### 星历：RINEX 3.04 导航文件

支持多系统混合电文。开普勒型（GPS / Galileo / BeiDou / QZSS / NavIC）解析
BROADCAST ORBIT 1–7 全部谐波改正项；GLONASS 与 SBAS 解析 XYZ + 速度 + 加速度。

### 轨迹：CSV / DAT

必需列（**列名不必是这七个**）：

| 列 | 单位 | 含义 |
|---|---|---|
| `Time` | s | 相对时间戳，间隔可不等 |
| `Longitude` | deg | 经度，东经为正 |
| `Latitude` | deg | 纬度，北纬为正 |
| `Height` | m | 大地高（椭球高） |
| `Yaw` | deg | 航向角，**正北 0，北偏西为正（+），北偏东为负（−）**，取值 (−180, +180] |
| `Pitch` | deg | 俯仰角，抬头为正 |
| `Roll` | deg | 滚转角，右滚为正 |

**关于列名、列序和列数**：工具先自动认列，认不出来才让你在面板里指一次。
- 列名可以是中文（`时间`/`经度`/`纬度`/`高程`/`航向角`/`俯仰角`/`横滚角`），
  也允许带单位后缀（`Height (m)`）——括号里的单位和各种分隔符会被剥掉再比对。
- **列顺序任意**：内部把「规范字段 → 真实列下标」做成映射，所以列怎么排都不影响。
- **多余的列照单全收**：不参与计算，也不会出现在导出里（导出的列是固定的，见「导出」）。
- 认不全就硬失败并点名缺哪几列，**不会**默默拿 0 顶替。

**关于文件格式**：`.csv` / `.dat` / `.txt` 走文本解析，分隔符自动嗅探——逗号、制表符、
分号、竖线，**都不认时退回空格**（定宽对齐的 `.dat` 也能切，连续多个空格按一个算）。
嗅探取表头那一行的列数为准，所以 `GPS Time, Longitude, …` 这种**字段名内部带空格**的
逗号文件不会被空格抢走。文本层还支持 RFC-4180 引号（样本 `train_set.csv` 的
`PRN_label` 就是 `"G01,G02"` 这种写法）。

**批量导入时映射只定一次**：一批里第一份轨迹文件自动认列，认出的映射直接套用到后面
每一份。所以面对上百份列名相同的轨迹文件，只需要对第一份指一次。后面每份的表头都会
和第一份比对一次，签名不同的单独标出来（`N 份表头不一致`），不会拿一套可能对不上的列
去解它。改映射会清空已解析结果、任务表与运行结果重新计算 —— 旧结果是用旧列算的，
留着比清掉更危险。

同一份格式由 **[sim-trace](https://github.com/your-id/sim-trace)** 生成。

## 坐标与姿态约定

- 机体轴：**X-右 / Y-前 / Z-上**（Z 即天线面法线）。
- 姿态 DCM：`C_enu^b = Ry(−roll) · Rx(−pitch) · Rz(−yaw)`，行向量为机体系轴在 ENU 中的表示。
- 可见判据**两条同时满足**才算计入：
  1. `z_b > sin(掩角)` —— 相对天线面法线的高度角高于掩角；
  2. `up > 0` —— 未被地球本体遮挡（地平线以下）。
- PDOP 由 `G = (HᵀH)⁻¹` 求得。未知量顺序是 `[钟差, x, y, z]`，故位置块取**右下** 3×3
  （**不含钟差**；GDOP 才是四项全取），再 `Cov_enu = Kᵀ·Cov_body·K` 转到当地 ENU，
  最后 `PDOP = √(σ_E² + σ_N² + 2σ_EN)`。可视星 < 4 时为 `NaN`。
- **星历选取**：取 `t_abs ≤ t` 中最新的一条；若该星首条电文晚于 `t`，则向前外推用首条。
  两条路径都要求落在 `±2 h`（`EPH_MAX_AGE`）窗内，超窗即把该 (历元, 星) 判为不可用。
  窗外的组合会在日志和状态栏以「星历过期 x%」报出。样本星历的最大偏差为 +1.39 h / −2.00 h，
  故默认窗对样本零丢弃。

## 批量任务

单任务界面除顶部新增的一个「批量任务」跳转按钮外**一行未改**。批量浮层自成一套输入、
一套掩角与星座选择、一套结果视图，与单任务状态完全隔离（`e2e_browser.js` 有一条断言
专门守着这条边界）。核心流水线 `parseRinex → buildLOSChunk → solveAll` 被原样复用，
所以批量与单任务的数值口径必然一致——实测同一份输入在单任务下是 53.413 星、批量模式下
是 53.413 星。

| 模式 | 固定文件 | 多选文件 | 差异来源 |
|---|---|---|---|
| ① | 轨迹 CSV | 多份星历 RINEX | 逐日星历差异 |
| ② | 星历 RINEX | 多条轨迹 CSV | 航迹/姿态差异 |

**两个模式各有一份独立现场，来回切不丢东西。** 切模式只是换一个 slot：文件选择、
解析结果、任务表、跑出的曲线、基准选择全部留在原处，切回来时逐位还原，连文件都不用
重选。掩角与起始时刻是两个模式共用的控件，因此结果标题会标注「这批结果是哪个模式、
哪个掩角、哪个起始时刻跑出来的」——改了参数再切回来，一眼就能看出该不该重跑。

（跑批期间模式选择会被锁死，否则正在写入的结果会落到另一个模式的现场里去。）

### 文件名的显示

浏览器自带的「未选择任何文件 / N 个文件」那一行是**不可程序化更新**的（`input.files`
只读），而切模式时要显示的其实是另一个 slot 的文件名，与 input 里存的那份并不是一回事。
所以原生 input 被藏起来，文件名一律由界面自己渲染——**固定文件与批量文件同这一套**：

| 状态 | 显示 |
|---|---|
| 未选 | `未选择` |
| 解析中 | `解析中 3/8 份：<当前文件名>` |
| 就绪 | `xxx.rnx · 96 颗星` / `xxx.csv · 5000 行` |
| 失败 | `xxx.rnx · 解析失败：轨迹 CSV 缺少必需列: …` |

多选按份数缩写，避免被省略号截掉份数：**1 份**写全名，**2 份**用「、」并排，
**≥3 份**写成 `第一个 等 N 份`；完整名单与「共 N 份，其中 M 份解析成功」挂在悬停提示上，
解析失败几份直接跟在后面（`… 等 8 份（2 份解析失败）`）——只报「选了 8 份」而不说
其中 2 份根本没进去，是最容易让人误读的一种显示。

### 起始时刻的锚定

轨迹的 `Time` 是相对秒，本身不含绝对日期。批量模式用一个显式的"起始时刻"把它锚到
UTC 上，锚定规则两种模式不同：

- **模式 ①** 各取该星历文件**电文最多的那一天** + 指定的时分秒。取"电文最多的一天"而不是
  "覆盖的第一天"是必须的：标称一天的文件常从前一日末尾就开始覆盖。样本
  `BRDM00DLR_S_20262690000` 覆盖 09-25 23:59:42 → 09-26 23:59:44，其中 09-26 有
  15060 条电文、09-25 只有 89 条——按覆盖起点锚会整整偏 12 小时，且所有任务都会被判过期。
- **模式 ②** 全部轨迹共用这一个绝对时刻，从完全相同的瞬间起算。

每个文件都会在运行前的预览表里给出**覆盖判定**：`ok`（轨迹全程落在星历覆盖内）、
`edge`（部分落在 `±2 h` 窗内）、`out`（基本无覆盖，此时跑出来的数值不可信，预览表会标红）。

### 模式 ② 的网格一致性

各条轨迹的历元数/步长/跨度可能不同（样本 `train_set.csv` 是 9 点 @3600 s，航班轨迹是
5000 点 @1 s）。这不影响统计量，但会让逐历元 CSV 出现无法对齐的 x 值，因此预览表会
单独标出网格是否一致，不一致时提示按汇总口径读数。

### 四个结果视图

| 视图 | 内容 |
|---|---|
| 对比曲线 | 全部任务的逐历元曲线。纵轴可在「Δ 基线」与「绝对值」间切换——Δ 口径下基准自身恒为 0（贴地直线），只有绝对值图能告诉你这个 Δ 是从多少降下来的。点击图例可更换基准任务 |
| 日期趋势 | 模式 ①：每个点 = 一份星历，横坐标为按锚定日期排序的序号 |
| 轨迹分布 | 模式 ②：每个点 = 一条轨迹，横坐标为平均高度 |
| 汇总表 | 每个任务的历元数、星数均值/极值、PDOP 均值/峰值、NaN 比例、过期率、耗时 |

### 导出

三个入口，文件名都带掩角（换掩角重导会另存一份，不覆盖）：

| 按钮 | 产物 |
|---|---|
| **导出科研数据 CSV**（单任务） | 逐历元，表头固定 15 列（见下） |
| **分任务导出 ZIP** | 一个 zip，**每个任务一个 csv**，与单任务导出**完全同一种形状**，成员名 `A_on_B_mask<掩角>_<NN>.csv` |
| 导出逐历元 CSV（合并全表） | 一张长表（`task,t0_utc,epoch,t_rel_s,visible_count,pdop,drop_rate`），所有任务首尾相接 |
| 导出汇总 CSV | 每个任务一行（`task,t0_utc,epochs,mean_visible,...,drop_rate,cover,ms`） |

**逐历元 csv 的列是固定的 15 列**，单任务导出与 zip 里的每个成员都用同一份生成逻辑：

```
Time,Longitude,Latitude,Height,Yaw,Pitch,Roll,Visible_Count,PDOP,PRN_label,PosAccH_m,PosAccV_m,VelAccE_mps,VelAccN_mps,VelAccD_mps
```

前 7 列是**映射后的标准名**，后 8 列是产出物（3 个几何 + 5 个精度）。源文件里的其余列一律不带走 ——
厂商备注、多余的实验列、乱序、中文列名，全都留在输入侧。既然已经付出了认列与
映射的代价，输出就该规范可控，而不是把不可控的输入形态原样传给下游。
合并全表和汇总表是**另一种产物**（按任务对比用的），保留 `task` 等列是有意为之。

**为什么打包成 zip 而不是逐份下载**：一批上百个任务就是上百次程序化下载，
浏览器从第 2 次起就会拦（"是否允许下载多个文件"），实际等于导不出来。
打包只触发 1 次下载，解压后正是想要的一份一个 csv。用浏览器原生的
`CompressionStream` 压缩，不引入任何依赖。

**命名规则**统一是 `A_on_B_mask<掩角>_<NN>.csv`：**A 是固定侧输入，B 是这个任务的输入**，
两种模式同一条规则（模式① A=轨迹、B=星历；模式② 反过来）。`NN` 是任务序号，
补零到同宽（100 个任务就是 `_001`…`_100`），所以文件管理器按名字排序就是数值顺序。
文件名里的中文、括号、空格都原样保留；只有 Windows 真正禁止的字符（`\ / : * ? " < > |`）
才会被替换，每段截断到 64 字符。

任务名、固定侧文件名、掩角、起始时刻都不再占列：文件名里已经带着 A、B 和掩角，
同一批任务又锚定在同一时刻，这些信息在单独一份 csv 里全是常量。

**文件名里的掩角取自跑这批时真正用的那个值**，不是当前滑块位置：批量掩角滑块只改参数、
不失效结果，拿滑块值命名会写出「23° 的数据标成 0°」这种文件名。

### 交叉验证（Python 参考实现）

`reference/ref_pdop.py` 是用不同语言、不同写法独立重写的一套实现，
`test_core.js` 把 JS 输出与它逐历元比对，并断言六组统计量的硬编码基准值：

| 场景 | 平均星数 | 平均 PDOP |
|---|---|---|
| 全部 7 系统，掩角 15° | 53.413 | 0.3915 |
| 仅 GPS | 7.347 | 1.1807 |
| 仅北斗 | 16.564 | 0.7405 |
| GPS + 北斗 | 23.911 | 0.5866 |
| GPS + 北斗 + Galileo | 31.102 | 0.5109 |

外加 7 组掩角扫描与 4 个抽样历元的逐值比对。PDOP 另有第三条完全独立的路径 ——
`test/tools/dop_ref.js` 用 Schur 补把 4×4 位置块化成 3×3 直接求逆，不经过被测代码里的
`matInv4` / `pdopFromQ`；三条路径在上述每一项上逐位一致（`test_core.js` §5b 有断言）。

> PDOP 曾在 `pdopFromQ` 与 `ref_pdop.py` 两处同时算错（取了对角元 `[0][4]+[1][5]+[2][6]`，
> 含了钟差方差又漏了 q_zz），系统性偏大 1.62~1.75 倍。现已两处一并修正。

### 实测基准回归（`test/fixtures/train_set.csv`）

2026-09-26 全天逐小时，在上海一点位（121.479216°E, 31.236807°N, h = 4 m, 姿态 0/0/0）
采集的真实接收机定位解算数据。仅 GPS、掩角 15°：

| 指标 | 结果 |
|---|---|
| 9 个历元中星数与实测完全相同 | **8 / 9** |
| 平均 \|ΔN\| | **0.111** |
| PRN 命中 | **74 / 75**（Jaccard 0.988） |
| 平均 \|ΔVDOP\|（见下） | **0.271** |

唯一未命中的 G10 仿真仰角 14.87°，恰好差 0.13° 落在 15° 掩角之下——掩角边缘的
正常抖动。

**这份数据集的 `PDOP_label` 列其实更像 VDOP，不是水平 PDOP** —— 卫星集合已经逐星
对上（PRN 命中 74/75、星数 8/9 完全一致），同一组视线单位矢量下 DOP 是唯一确定的，
所以不可能是几何算错了。三种读法的实测对比：

| 与实测列的对照 | 相关系数 | 平均 \|Δ\| |
|---|---|---|
| 等权 PDOP | 0.666 | 1.016 |
| sin²(el) 加权 PDOP | −0.354 | 0.310 |
| **等权 VDOP** | **0.974** | **0.271** |

第一行形状对不上，第三行形状与量级都对得上且相关性极高。这里**如实记录而不是调容差
糊过去**：仿真侧按 PDOP 定义输出，实测侧那一列的口径需要向数据集作者确认；在口径确认
之前，测试里改成断言 VDOP 并把两者的量级差显式断言为「大于 0.6」，这样口径一旦被改
回来，测试会立刻失败而不是继续放行。

该数据集由项目作者于 2026-09-26 实地采集。每个历元的实测星空图截图与 CSV 逐行
一一对应，放在同一目录下：第 `Time` = 3600·k 秒的行对应 `fixtures/sky-ref/UTC-kh.png`
（k = 0…8），对照排查时可直接看图核星。

### 已修复的算法缺陷

项目早期版本存在六处**互相独立**的算法错误，均由数据自身的不变式或独立实现的比对证伪。
它们已被逐条修复，并各自补上了能抓住它们的物理判据：

| # | 缺陷 | 判定依据 | 修复前 → 修复后 |
|---|---|---|---|
| 1 | 开普勒传播的纬度幅角漏掉真近点角 `ν` | 相邻两条电文推到同一时刻应位置一致 | 残差中位数 **8380 m** → **2.86 m** |
| 2 | ECEF→ENU 只做经度旋转，缺纬度旋转 | 合成天顶 LOS 应得仰角 90° | **31.2°** → **90.0°** |
| 3 | 地球自转改正（Sagnac）误用绝对 GPS 秒 | 应对合成正北方位无偏转 | 偏 **259.55°** → 0.0003° |
| 4 | `Crs` 从历元行的 IODE 槽位读取 | 丢失最大 ~150 m 径向谐波 | `Crs ≡ 0` → 正确值域 ±95 m |
| 5 | `pdopFromQ` 取对角元 `[0][4]+[1][5]+[2][6]`，含钟差方差又漏 q_zz | Schur 补独立路径（`test/tools/dop_ref.js`） | 0.6224 → 0.3844（偏大 1.62×） |
| 6 | 同上，取的是**机体系** x/y 的对角元，等于假设天线面板始终水平 | 把机体系 LOS 先转回 ENU、直接在 ENU 里累加 | 均值 0.3844 → **0.3915**，峰值 0.6877 → **1.2826** |

缺陷 1 尤其隐蔽：它让卫星被冻结在各自轨道上的同一点，星空图全天不转，而当时
全部 16 项自检**照样全绿**（`|lat| ≤ |i0|`、轨道半径在标称带内等判据在冻结状态下
都成立）。因此自检面板新增了三条**时间相关**的物理判据——这类判据是唯一能抓住
它的：

1. **相邻电文自洽性**：同一卫星相邻两条广播电文推到同一时刻，位置差中位数须 < 50 m；
2. **纬度必须随时间变化**：`|Δlat(t, t+600 s)| > 0.05°`；
3. **ENU 合成向量**：天顶 → 仰角 90°，正北/正东 → 仰角 0°、方位 0°/90°。

## 定位 / 测速精度模型

除几何精度因子外，工具还按**一台标准单频多星座导航接收机**的误差预算，逐历元输出五个
标准差：

| 输出列 | 含义 | 单位 |
|---|---|---|
| `PosAccH_m` | 水平位置精度 σ_h | m |
| `PosAccV_m` | 高程位置精度 σ_v | m |
| `VelAccE_mps` | 东向测速精度 σ_ve | m/s |
| `VelAccN_mps` | 北向测速精度 σ_vn | m/s |
| `VelAccD_mps` | 垂向测速精度 σ_vu | m/s |

这些数字**由广播星历 + 单频模型主导，不是接收机的标称精度**：一颗只播广播星历的接收机
本来就不可能比星历本身更准。

### 误差预算

单历元每颗参与解算的卫星先算出一个 UERE（用户等效量测误差）标准差，再由加权最小二乘
反解协方差：

```
σ_i² = σ_码热² + σ_多路径² + σ_相位中心² + σ_对流层残差² + σ_电离层残差² + σ_钟差² + σ_广播星历²
```

**关键口径：进预算的是「残差」，不是被改正掉的总量。** 接收机施加 Klobuchar 单频电离层
改正与 Saastamoinen 对流层改正之后，剩余的量才进误差预算。若把总延迟当误差算进去，
低高度角处会虚高 2~3 倍，σ_h 会从 1.3 m 变成 5.8 m 量级 —— 方向完全反了。

| 分量 | 取值 | 说明 |
|---|---|---|
| 码热 σ_th | 0.3 m | C/A 或 B1I 一个码片 |
| 多路径 σ_mp | 0.3 + 3·exp(−(el−5°)/10) m | 随高度角衰减 |
| 相位中心 σ_pcv | 0.5 m | 天线 PCV |
| 对流层残差 | 0.5 m | Saastamoinen + 标准大气改正后 |
| 电离层残差 | 0.4 × Klobuchar 延迟 | 单频改正消掉约 60% |
| 钟差 σ_clk | 0.5 m | 卫星钟差残差 |
| **广播星历 σ_eph** | **见下表** | **主导项** |

σ_eph 取各星座广播星历的**规格量级差分轨道误差**（1σ，米），不是本仓库样本的实测中位数
—— 后者是「同星相邻电文互推差值」，被每条电文各自的 `a0` 钟差多项式主导，且尾部混有
记录边界垃圾（样本里 BDS 最大 1.3×10⁷ m），当轨道误差用会让 σ_h 放大约 10 倍。

| GPS | 北斗 | Galileo | QZSS | IRNSS | GLONASS | SBAS |
|---|---|---|---|---|---|---|
| 1.5 | 2.5 | 1.5 | 1.5 | 2.0 | 3.0 | 3.0 |

σ_eph 是主导项：把它设为 0，σ_h 从 1.25 m 降到 0.65 m；设成 4 倍则升到 3.37 m。
换句话说，本工具给出的 σ_h 里有约 3/4 的方差来自广播星历本身。

### 几何与方向约定

位置用**加权**法方程（权 = 1/σ_i²，未知量 `[钟差, x, y, z]`，4×4）；测速用载波多普勒，
噪声在卫星间近似共模，故用**无权**的 3×3 法方程（未知量只有 `[vE, vN, vU]`），
乘 σ_doppler = 0.12 m/s。两者都在机体系解出后再转到 ENU：

- `σ_h = √(q_EE + q_NN + 2·q_EN)`，`σ_v = √(q_UU)`，`σ_ve = σ_d · √((D⁻¹)_EE)` 等；
- 可视星 < 4 或求逆失败时输出 `NaN`，导出 CSV 里留空（**不写 0** —— 0 会被当成完美精度）。

**测速 σ_vu < σ_ve 是正确的，不是 bug。** 教科书里 "VDOP > HDOP" 只对**位置解**成立
（位置法方程含钟差未知量）；测速解没有钟差未知量，性质反过来。可见星是一顶以天线视轴
为轴的锥帽，视轴方向（≈当地天顶）正是方位展开不足的方向，恰好是锥帽对称轴，被约束得
最好。用 8 星、方位均匀、仰角 45° 的合成算例验证：解析环模型给出 HDOP = 2.000、
VDOP = 1.414，本实现算出的 VE/√n = 0.7071、VU/√n = 0.5000 逐位吻合。

### 交叉验证

面板上的「MC」列是**同一误差预算下的真实最小二乘解**：在真值处线性化（真值能精确复现
全部伪距），每个历元抽 20 次、每星按各自 σ_i 抽噪声，解出 Δx、Δv 后取 RMS。5 个量与
确定性 σ 的偏差全部落在 **3% 以内**（4 组场景 × 5 个量 = 20 项，最大 2.9%）。这既是
模型自洽性检查，也是 `test/test_core.js` 的回归护栏之一。

### 近似与口径说明

- **Galileo 的电离层系数回退到 GPS 的 Klobuchar α/β**。样本 RINEX 里 `GAL` 标签下只有
  3 个系数（`1.2100e+02 6.2500e-02 6.1035e-05`），是 Nequick 而不是 Klobuchar。两者日变化
  量级相近，故借用并在此标注为近似。
- **Klobuchar 的 t 用该星座系统时的当日秒数**。BDS 用 BDT，比 GPS 慢 14 s（样本
  `BDUT ... 14 2437` 行已证实），代码里按 `SYS_TIME_OFF = {C: -14}` 修正。QZSS/IRNSS
  偏移在亚微秒量级，忽略。
- **relativistic 钟差改正已经在星历传播里生效**，不再单独进预算；本仓库样本的 GPS 轨道
  e ≈ 0.002，改正量中位数仅 0.6 m，不是主导项。

## 已知限制

- 精度输出**不含**多路径的统计相关性、接收机钟差与多普勒的共用、以及姿态误差的传播 ——
  这些都要具体接收机型号才谈得上。
- 轨迹的 `Time` 是相对时间戳，不含绝对日期。单任务下星历的绝对时刻通过"轨迹首历元对齐"
  样本星历首条电文"隐式确定。换用不同日期的星历时需自行确认这一对应关系，
  并留意状态栏的「星历过期」比例——它正是这一对应关系出错的直接指示。
  批量模式下这一对应关系被提到了明面上（起始时刻字段 + 覆盖判定），但锚定日期仍是**推定**
  的：若某份星历的电文集中度不足以唯一确定"那一天"，需人工核对预览表里的锚定日期。
- `Height` 按椭球高直接使用，不做大地水准面改正。
- 仅支持广播星历，不支持精密/快速星历。
